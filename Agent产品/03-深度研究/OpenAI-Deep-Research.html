# 推理模型 + 浏览工具，循环由模型自己驱动
q = clarify(user_question)                 # 先问清楚
notes = []
while not enough(notes):
    act = model(q, notes)                  # 推理后决定下一步
    if act.type == "search": notes += search(act.query)
    if act.type == "open":   notes += read(act.url)   # 记下来源
    if act.type == "python": notes += run(act.code)
report = model.write(q, notes)             # 正文里插引用

检索与引用

读得多，留得少

  • 多轮迭代：一次搜索不够，按读到的内容生成新查询
  • 边读边记：只把有用的片段和来源记下，不把整页塞进上下文
  • 交叉验证：同一事实找多个来源，冲突时说明
  • 引用绑定：论点和来源一一对应，减少编造
  • 透明：侧边栏显示思考过程和访问过的网页
仍会出错：可能引用不权威的来源，或对不确定的结论过于自信。引用是让人能核查，不是保证正确。

设计亮点

🏋

RL 训练，不靠编排

没有手写的“规划→搜索→总结”流水线，策略是练出来的，能在新问题上灵活应变。

⏱

用时间换质量

允许跑 5~30 分钟，后台运行，做完通知。把“等”变成产品的一部分。

🎯

先澄清再动手

长任务开跑前问清楚，成本最低。自己用 API 搭时要自己做这一步。

📊

常见问题

Q1Deep Research 和普通 RAG 有什么区别？
参考答案
  • 轮数：RAG 一般检索一次；Deep Research 几十轮
  • 主动性：模型自己决定查什么、读什么、何时停
  • 推理：读完会分析、对比、算数，不只是拼接片段
  • 代价：慢、贵，适合复杂调研，不适合简单问答
Q2为什么开跑前要问澄清问题？
参考答案
  • 任务长：跑偏了浪费几十分钟和大量 token
  • 问题模糊：用户一开始常说不清范围、深度、侧重点
  • 成本最低：在开头确认，比中途纠正便宜得多
Q3自己做一个 Deep Research，怎么设计？
参考答案
  • 拆问题：规划子问题，可以并行派给子 Agent 搜
  • 压缩：每个子 Agent 只返回要点和来源
  • 停止条件：预算上限 + 模型判断信息是否够
  • 写作：最后一个模型统一成文，校验每条引用
Q4怎么减少报告里的幻觉？
参考答案
  • 引用绑定：每个论点必须对应来源
  • 多源验证：关键事实至少两个来源
  • 来源分级：优先官方、论文，降低论坛权重
  • 表达不确定：证据不足时明说
