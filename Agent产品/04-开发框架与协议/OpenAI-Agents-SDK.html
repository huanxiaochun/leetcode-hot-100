核心工作原理

STEP 1
调用模型
当前 Agent 的指令 + 工具 + 历史
→
STEP 2
有最终输出
符合 output_type 就结束
→
STEP 3
有 Handoff
切换当前 Agent，继续循环
→
STEP 4
有工具调用
执行工具，结果追加，继续循环
↻ Runner 一直循环，直到出最终结果或超过 max_turns；全程自动记 trace

@function_tool
def get_order(order_id: str) -> str:   # 签名和注释自动生成 schema
    return "已发货"

refund = Agent(name="退款", instructions="处理退款")
triage = Agent(name="分诊", instructions="判断问题类型",
               tools=[get_order], handoffs=[refund])

result = Runner.run_sync(triage, "我要退款")
print(result.final_output)

关键组件

🤖

Agent

LLM + 指令 + 工具 + 可选的结构化输出类型。本质是一份配置。

🔁

Handoff

移交给另一个 Agent。对模型来说就是一个 transfer_to_xxx 工具。

🛡

Guardrail

输入 / 输出校验，和 Agent 并行跑。触发 tripwire 直接抛异常中断。

▶

Runner

执行循环。run 异步、run_sync 同步、run_streamed 流式。

🔭

Tracing

默认开启，记录每次模型调用、工具、handoff、guardrail，可接第三方平台。

🧰

工具类型

函数工具、托管工具（搜索、文件检索等）、MCP Server、把 Agent 当工具。

上下文管理

分清两种“上下文”

  • 本地上下文：RunContextWrapper 带的依赖对象（用户信息、DB 连接），工具能拿到，模型看不到
  • LLM 上下文：指令、对话历史、工具结果，模型真正看到的内容
  • Session：自动存取多轮历史，不用每次手动拼 to_input_list()，有 SQLite 等实现
  • Handoff 过滤：移交时可用 input_filter 裁剪历史，下一个 Agent 不必背全量

设计亮点

🪶

原语少

几个概念就能写多 Agent，编排用普通 Python 控制流，不用学新 DSL。

🔀

两种协作模式

Handoff：对方接管对话。Agent as tool：调完回来，主 Agent 保持控制。

⚡

护栏并行

便宜模型做校验和主 Agent 同时跑，不合规就提前中断，省钱又不加延迟。

🔍

可观测开箱即用

不写一行代码就有 trace，可直接用于评测和调优。

背景：OpenAI 宣布可视化的 Agent Builder 会下线，要用代码编排的场景官方推荐 Agents SDK。

常见问题

Q1Handoff 和 Agent as tool 怎么选？
参考答案
  • Handoff：控制权转走，新 Agent 直接面对用户，适合客服分诊
  • Agent as tool：子 Agent 只返回结果，主 Agent 汇总，适合研究、拆任务
  • 判断标准：后续对话该谁负责
Q2Guardrail 是怎么工作的？
参考答案
  • 输入护栏：只在第一个 Agent 上跑，检查用户输入
  • 输出护栏：只在产出最终结果的 Agent 上跑
  • tripwire：返回触发标记，Runner 抛异常，业务层捕获处理
  • 实现：可以是规则，也可以是另一个小 Agent
Q3Handoff 在模型层面是怎么实现的？
参考答案
  • 伪装成工具：每个 handoff 注册为一个 transfer_to_<agent> 函数
  • Runner 拦截：模型调了这个工具，Runner 换掉当前 Agent 的指令和工具
  • 历史：默认带上全部对话，可用过滤器裁剪
