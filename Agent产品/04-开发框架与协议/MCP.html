FRAMEWORK / PROTOCOL

MCP

产品定位

Model Context Protocol：AI 应用接外部工具和数据的统一插口，常被比作 AI 的 USB-C
发起
Anthropic，2024-11 开源
治理
2025-12 捐给 Linux 基金会下的 AAIF
形态
开放协议 + 多语言官方 SDK
底层
JSON-RPC 2.0
一句话记住：把 M 个应用 × N 个工具 的对接，变成 M + N。工具写一次 Server，所有支持 MCP 的应用都能用。

核心工作原理

HOST
宿主应用
Claude Desktop、IDE、自研 Agent，管 LLM 和用户
→
CLIENT
客户端
Host 内部，每个 Server 一个，1 对 1 连接
→
SERVER
服务端
包装 GitHub、数据库、文件系统等能力
↻ 初始化协商能力 → tools/list 拿工具清单给 LLM → LLM 选工具 → tools/call 执行 → 结果回填上下文
// Client → Server：调用工具
{"jsonrpc": "2.0", "id": 3, "method": "tools/call",
 "params": {"name": "get_weather", "arguments": {"city": "北京"}}}

// Server → Client：返回结果
{"jsonrpc": "2.0", "id": 3,
 "result": {"content": [{"type": "text", "text": "晴 22℃"}]}}

关键组件

🔧

Tools

模型控制。可执行的函数，带 JSON Schema 参数，由 LLM 决定何时调用。

📄

Resources

应用控制。按 URI 读取的数据，如文件、表结构，由 Host 决定塞不塞进上下文。

💬

Prompts

用户控制。预置的提示模板，常以斜杠命令的形式给用户选。

🧠

Sampling

反向能力：Server 请 Client 调一次 LLM，Server 自己不用持有模型 key。

🙋

Elicitation

反向能力：Server 执行中途向用户要补充信息，如确认、填表。

📁

Roots

Client 告诉 Server 可操作的目录边界。

传输与安全

两种标准传输

  • stdio：Host 拉起本地子进程，走标准输入输出，适合本地工具
  • Streamable HTTP：一个 HTTP 端点，可按需升级为 SSE 流，适合远程服务
  • 旧 HTTP+SSE：早期双端点方案，已被 Streamable HTTP 取代

安全要点

  • 授权：远程 Server 用 OAuth 2.1，Server 是资源服务器
  • 用户确认：规范要求敏感工具调用前让用户知情、可拒绝
  • 工具投毒：工具描述里藏指令，会被 LLM 当真
  • 数据外泄：多个 Server 混用时，一个恶意 Server 可诱导模型把别家数据带走
新动向：2026-07 版规范把协议层改成无状态，去掉了会话和 Mcp-Session-Id，远程 Server 更容易水平扩展。

常见问题

Q1有了 Function Calling，为什么还要 MCP？
参考答案
  • 层次不同：FC 是模型怎么表达“我要调工具”，MCP 是工具怎么被发现和执行
  • 互补：Host 把 MCP 的工具清单转成 FC 格式喂给模型
  • 价值：工具一次实现、到处复用，还带资源、提示、授权等标准
Q2Tools、Resources、Prompts 有什么区别？
参考答案
  • 区别在谁触发：Tools 由模型调，Resources 由应用选，Prompts 由用户点
  • 副作用：Tools 可以有副作用，Resources 只读
  • 举例：查数据库是 Tool，表结构是 Resource，“生成周报”模板是 Prompt
Q3工具接了几百个，模型选不准、上下文爆了怎么办？
参考答案
  • 按需加载：先给工具摘要或检索工具，命中后再展开完整 schema
  • 分组：按任务只挂相关 Server，或拆给子 Agent
  • 写好描述：工具名和描述要区分度高，参数尽量少
  • 压缩结果：工具返回大结果时截断或摘要，别全量塞回
Q4MCP 有哪些安全风险？怎么防？
参考答案
  • 工具投毒：只装可信 Server，审核描述，版本锁定防“先好后坏”
  • 提示注入：工具返回内容当数据，不当指令
  • 越权：OAuth 最小权限，token 不透传给下游
  • 兜底：敏感操作人工确认，本地 Server 跑在沙箱里
