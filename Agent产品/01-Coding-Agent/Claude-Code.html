工具加载机制

核心矛盾：工具越多，越占上下文

每个工具的 JSON Schema 都要放进提示词。接几个 MCP server 就是几十个工具，光定义就能吃掉上万 token，模型选工具也更容易选错。

所以 Claude Code 按「常用程度」分层加载：常驻的给全量，不常用的只给名字，用到再取。

来源启动时放进上下文的什么时候拿到全部内容
内置工具完整 schema（Read、Edit、Bash、Grep…）一直在
MCP 工具只有工具名，如 mcp__github__create_pr模型调 ToolSearch 取回 schema 后才能调用
Skills只有 name + 一句话 description调用 Skill 时才加载 SKILL.md 正文，附带的脚本 / 文档再按需读
子代理类型名 + 用途说明派任务时新开上下文，只带它定义里允许的工具
# 延迟加载：上下文里只有名字，没有参数定义
# 模型想用 WebFetch → 先搜 schema → 再调用
ToolSearch(query="select:WebFetch")   # 返回完整 JSON Schema
WebFetch(url="...", prompt="...")      # 现在可以正常调用了

一次工具调用的完整链路

1
模型发出 tool_use
一轮可以同时发多个互不依赖的调用
2
PreToolUse Hook
用户配置的脚本先过一遍，可以改参数
allow → 免弹窗（deny / ask 规则照样生效）
拦截 → 原因回给模型
3
权限检查
按 allow / deny 规则和当前权限模式判断
命中 allow → 直接执行
没命中 → 弹窗问用户
deny 或用户拒绝 → 告诉模型被拒
4
执行工具
真正读文件、跑命令、调 MCP server
5
PostToolUse Hook
拿到结果后再跑脚本，比如自动格式化、记日志
↻
结果作为 tool_result 回到消息历史
成功、报错、被拒都会回给模型，由它决定下一步
这套思路叫渐进式披露：先给目录，用到再展开。Skills 和延迟加载的 MCP 工具都是这么做的。

上下文与缓存

模型不记得上一次请求，每轮都把全部内容重发一遍

所以要管两件事：窗口装得下（压缩），重发得便宜（缓存）。

1窗口里装了什么

时机进入上下文的内容
开口之前系统提示、CLAUDE.md、MEMORY.md、MCP 工具名、Skill 描述、环境信息
干活过程中读的每个文件、命令输出、匹配到的路径规则、Hook 输出
派子代理只进来调用参数和一段总结，子代理读的文件留在它自己的窗口

2快满了：压缩

  • 自动压缩：接近上限时把对话换成一份结构化摘要，会话不中断
  • 手动压缩：/compact 重点保留 auth 的修复，自己指定摘要保留什么
  • 局部压缩：/rewind 选一条消息，只压缩它之前或之后的部分
  • 换任务：/clear 清空，旧对话不再占位置和费用
压缩后内容
从磁盘重新注入根目录 CLAUDE.md、auto memory、Skill 描述、plan 模式写的计划
重读文件最近改过的最多 5 个文件；超过 5,000 token 的只给路径
重新注入 Skill 正文每个最多 5,000 token，总共 25,000，超了先丢最早的
被总结掉子目录 CLAUDE.md、带 paths: 的规则，下次读到对应文件再加载
Skill 正文超长时保留开头，所以最重要的指令写在 SKILL.md 最前面。

3重发得便宜：Prompt Caching

API 按请求开头（前缀）做精确匹配，前缀里任何一处变了，后面全部重算。所以 Claude Code 把最不常变的放最前面：

1
系统提示 + 工具定义
工具集合变了才变
2
项目上下文
CLAUDE.md、auto memory；会话开始、/clear、/compact 时才变
3
对话
每轮只在末尾追加，前面的都能命中缓存
✗

会让缓存失效

切模型、开 fast mode、增删 MCP server、开关插件、整个禁用一个工具、压缩、升级版本。

✓

不影响缓存

改仓库文件、会话中改 CLAUDE.md、切权限模式、调用 Skill、rewind。这些内容都追加在对话末尾。

  • 有效期：默认 5 分钟没请求就过期；订阅用户的主对话用 1 小时
  • 子代理：系统提示不同，从零建自己的缓存；fork 继承父对话，能直接命中父的缓存
  • 批量派活：workflow 同时起一批相同前缀的 agent 时，先放第一个，其余最多等 5 秒，让它们读到第一个写好的缓存

安全模型

三层叠加：权限模式定基线，规则做例外，沙箱兜底

权限决定要不要问人，沙箱决定命令跑起来能碰到什么。两者互相独立。

1权限模式：哪些操作不用问

模式不问就能做的适合
default（Manual）只有读敏感操作，每步自己看
acceptEdits读、改文件、mkdir / mv 这类常见文件命令边看边改代码
plan读和探索，不改源码，计划批准后才能动手动手前先调研
auto全部，由分类器模型在后台审核长任务，减少弹窗
dontAsk只有预先批准的工具，其余直接拒绝CI、脚本
bypassPermissions全部只在隔离的容器 / 虚拟机里用
  • 规则叠在模式上：allow / ask / deny，例如 Bash(npm test)；deny 在任何模式下都生效，包括 bypass
  • 任何模式都不自动放行：命中 ask 规则的、需要用户交互的工具、删除关键路径（如 rm -rf ~）
  • Hook 不能越权：PreToolUse 返回 allow 也绕不过 deny / ask 规则

2Auto mode：用另一个模型代替人审批

1
先查规则
命中 allow / ask / deny 就直接按规则办
2
低风险直接过
只读操作、工作目录内改文件
3
其余交给分类器
拦超出用户要求、碰陌生基础设施、像是被读到的内容诱导的操作
通过 → 执行
拦截 → 把命中的策略名告诉模型

3沙箱：限制 Bash 能碰到什么

维度默认
写只能写工作目录和临时目录
读大部分机器可读，用 denyRead 挡掉 ~/.ssh 这类凭据
网络没有直连，走本机代理按域名白名单放行，白名单默认为空
  • 实现：macOS 用 Seatbelt，Linux / WSL2 用 bubblewrap，开源为 sandbox-runtime
  • 只包 Bash：Read / Edit / WebFetch 走权限规则；Hook、MCP server 也不在沙箱里
  • 换来少弹窗：auto-allow 模式下，在沙箱里跑的命令直接放行

在固定时机跑你自己的逻辑，结果是确定的，不靠模型自觉

比如「每次改完文件自动格式化」「禁止改 .env」，写进 CLAUDE.md 模型可能忘，写成 Hook 一定执行。

继承完整对话、工具和模型，不用重新交代背景，能命中父的缓存。

  • 自定义：.claude/agents/*.md，frontmatter 写工具白名单、模型、权限、Hook

2Agent teams

  • 组成：lead（主会话）+ 成员（独立 Claude 实例）+ 共享任务列表 + 信箱
  • 协作：成员自己认领任务，完成后自动解锁依赖它的任务；成员之间直接发消息、互相质疑
  • 适合：多方向并行调研、前后端分人负责、多个假设同时验证；token 开销明显更高

  • 可以固化质量流程：比如每条发现都派独立 agent 反向验证，过了才报告
  • 适合：全仓库扫 bug、几百个文件的迁移、需要多来源交叉核对的调研

较新的设计

{}

Code Mode

模型不再一次调一个工具，而是写一段 JS 批量调用：并行跑命令、把上一步结果喂给下一步，只把需要的部分返回给自己。

适合跨很多文件的重复改动、结果要先过滤再看的搜索。auto mode 下分类器审的是这段代码，不是里面每个调用。

🎓

Advisor

主模型干活，关键时刻请更强的模型给意见：定方案前、同一个错反复出现时、宣布完成前。

顾问看到完整对话，在服务端运行；什么时候问由主模型决定。开关它不影响主模型的缓存。

🎯

/goal

给一个完成条件，每轮结束后由另一个小模型判断：没达成就继续，达成或判定做不到就停。

本质是一个用提示词判断的 Stop Hook。好处是完成与否不由干活的模型自己说了算。

常见问题

Q1为什么 Claude Code 不用 RAG 检索代码？
参考答案
  • 新鲜度：代码频繁变，索引要不停重建，grep 永远是当前状态
  • 精确性：找函数名、报错信息这类精确匹配，grep 比语义检索准
  • 简单：不需要额外的索引服务，代码不出本机
  • 代价：多花几轮工具调用和 token，靠模型能力和缓存抵消
Q2长任务上下文爆了怎么办？
参考答案
  • 压缩：早期对话总结成摘要，保留关键决策和文件路径
  • 隔离：探索类工作派给子代理，主上下文只收结论
  • 外部化：进度写进 Task 待办工具 / 文件，状态不只存在对话里
Q3Agent 能跑任意命令，安全怎么保证？
参考答案
  • 分级权限：只读放行，写和执行要确认，可设白名单
  • Hooks：工具调用前后跑自定义脚本，可以拦截危险操作
  • 沙箱：限制文件系统和网络访问范围
  • 提示注入：工具返回内容当数据，不当指令
Q4接了几百个工具，上下文和选工具准确率怎么办？
参考答案
  • 延迟加载：只放工具名，模型用 ToolSearch 按需取 schema
  • 渐进式披露：Skills 只放一句描述，调用时才加载正文
  • 子代理裁剪：每类子代理只带自己需要的工具
  • 附带好处：常驻前缀稳定，prompt cache 命中率高
Q5Agent 的长期记忆怎么设计？为什么不用向量库？
参考答案
  • 两类：人写的规则（CLAUDE.md）+ Agent 自己记的经验（auto memory）
  • 索引常驻，正文按需：MEMORY.md 每次加载，相关条目再读全文
  • 写入有规矩：分类型、带原因、去重、记错就删，代码里有的不存
  • 为什么用文件：记忆条数少，模型看索引就能挑；纯文本人能直接看和改，可以进 git
Q6怎样让长会话的 prompt cache 命中率高？
参考答案
  • 原理：按前缀精确匹配，前面任何一处变了，后面全部重算
  • 排序：系统提示和工具定义 → 项目上下文 → 对话，越不常变越靠前
  • 只追加：plan 模式说明、Skill 正文、文件变化提醒都作为消息追加到末尾，不改前缀
  • 避免：中途切模型、增删 MCP server、频繁压缩
Q7auto mode 让模型审批模型，怎么防止被绕过？
参考答案
  • 规则优先：deny 规则、关键路径删除不经过分类器，分类器也放行不了
  • 隔离输入：分类器看不到工具返回内容，提示注入影响不到它；服务端另有探针扫描工具结果
  • 收权：进入 auto 时去掉 Bash(*) 这类宽泛的 allow 规则
  • 纵深：再叠一层沙箱，审批漏了也碰不到凭据和外网
Q8子代理、Agent teams、Workflow 怎么选？
参考答案
  • 子代理：任务独立、只要结果，比如搜代码、跑一轮调研
  • Agent teams：成员之间要讨论、互相质疑，比如并行验证几个假设
  • Workflow：几十上百个 agent、流程固定、要能复跑，比如全仓库迁移
  • 判断依据：谁持有计划，中间结果放哪，能不能接受更高的 token 开销
