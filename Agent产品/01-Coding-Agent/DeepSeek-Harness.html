一句话记住：Claude Code 是一个做好的产品，DSH 是一套拼产品的积木。模型适配、工具、沙箱、会话存储，连 agent loop 本身都是可替换的插件，下一节用一个真实插件讲清楚。

先分清：什么是 harness

Agent = 模型 + harness。harness 是夹在模型和你电脑之间的那层程序：决定模型怎么调工具、怎么改文件、怎么跑命令、怎么记住做到哪了。

同一个模型换个 harness，表现能差很多。DeepSeek 自己做 harness，是为了把模型和运行时一起调优。

插件系统

先把「插件」落到实处：它就是一个 JS 文件，导出三样东西

  • name：我叫什么
  • inject：我要用到哪些服务，比如 ['tools']。这些服务没准备好之前，我不启动
  • apply(ctx)：启动时做什么。ctx 是一块所有插件共用的「公告板」，上面挂着各种服务

1和普通程序比，差在哪

普通 Agent 程序

主函数里把每个部件写死：

main():
  llm   = DeepSeekClient()
  tools = [Read(), Edit(), Bash()]
  log   = JsonlLog()
  run_loop(llm, tools, log)

想换模型、加工具，得改 main 重新编译。

DSH

主程序只做一件事：读一张配置表，按行加载插件。

- id: llm-deepseek     # 模型适配
- id: tool-bash        # 一个工具
- id: session-jsonl    # 会话存储
- id: agent-loop       # 循环本身
# ……默认 Web 版近 300 行

换一行、删一行、加一行，就是换部件。

2一个完整的插件：给模型加一个「统计字数」工具

// word-stats.mjs（据第三方实测改写的简化版；原版 28 行，在 npm 安装版上跑通）
import { readFile } from 'node:fs/promises'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name   = 'word-stats-tool'
export const inject = ['tools']          // ① 我依赖 ctx.tools 这个服务

export function apply(ctx) {               // ② 启动时被调用
  ctx.tools.register(defineTool({          // ③ 往工具服务里登记一个工具
    name: 'word_stats',
    description: '统计工作区里一个文本文件的行数、词数、字符数',
    parameters: { path: { type: 'string', required: true } },
    output: { schema: { type: 'string' } },
    async execute(args) {                  // ④ 模型调用时真正执行的代码
      const text = await readFile(args.path, 'utf8')
      return `lines=${text.split('\n').length - 1} words=… chars=…`
    },
  }))
}
# patch.yml：把它插进配置表
- insert:
    - id: word-stats
      name: './word-stats.mjs'

3插件和工具有什么区别

工具是给模型用的，插件是给程序用的

工具是模型能看到、能主动调用的一项能力。插件是程序启动时加载的一段代码，它往系统里登记东西，登记的可以是工具，也可以是别的。

🧩

插件：word-stats.mjs

dsh 启动时读配置表，加载这个文件，调用它的 apply(ctx)。模型完全不知道这个文件存在。

🔧

工具：word_stats

插件登记进去的东西。有名字、描述、参数 schema，出现在发给模型的工具列表里，由模型决定什么时候调用。

工具插件
谁用它模型程序（dsh 启动时加载）
模型看得到吗看得到，schema 在提示词里看不到
什么时候起作用模型决定调用时启动时加载，之后一直在
由什么组成名字 + 描述 + 参数 + 执行函数name + inject + apply(ctx)
  • 一个插件可以登记多个工具：MCP 插件连上一个 server，会把这个 server 的所有工具都登记进去
  • 很多插件一个工具都不登记：下面讲的拦截 rm -rf 的插件只监听事件；模型适配器、沙箱后端、会话存储、会话日志上传也都是这类。它们改变程序怎么运行，模型调不了它们
在 dsh 里，工具只是插件能提供的东西之一。插件还能提供模型适配器、事件监听、沙箱、存储，甚至 agent loop 本身。
Claude Code 的说法不同，但层级一样：Plugin 是外层的安装包，里面的 MCP 配置最后给模型带来工具。

4插件之间怎么配合：服务 + 事件

⬆

提供服务

「我就是工具注册表」：在 ctx 上占一个名字，比如 ctx.tools。别的插件按名字找它，不 import 具体实现。

⬇

使用服务

「我往注册表里加东西」：上面的 word_stats 就是这种，调用 ctx.tools.register()。

👂

监听事件

「有工具要执行时叫我一声」：监听 tools/pre-execute，可以放行、拦截或改参数。

// 示意代码（签名做了简化）：一个禁止 rm -rf 的插件，只靠监听事件
export const inject = ['tools']
export function apply(ctx) {
  ctx.on('tools/pre-execute', async (call, next) => {
    if (call.name === 'bash' && /rm\s+-rf/.test(call.args.command))
      return { decision: 'deny', reason: '不允许 rm -rf' }  // 不调 next()：到此为止
    return next()                                          // 交给下一个监听者
  })
}
派发方式一句话DSH 里的例子
emit广播通知，不要返回值tools/result：工具结果出来了，记日志、算指标
waterfall洋葱式中间件，一层包一层，调 next() 往里传tools/pre-execute、tools/execute、llm/stream
serial按顺序一个个等它做完agent/turn-stopping：一轮要结束了，谁还想让它继续
Cordis 还有 parallel（同时通知、等全部完成）和 bail（依次问、谁先给答案就停）两种派发方式，写插件时按需要选。

一轮怎么跑

1

step

一次模型请求，加上它调用的工具。

n

turn

零到多个 step。领到第一条输入时开始，没有欠着的工作时结束。

1
领取输入
下一步的输入，加一条排队中的用户消息
2
拼提示词和工具
记下这一步用哪个模型；只放这一步被允许的工具 schema
agent/pre-step：放行或改写消息
拒绝 → 这一轮不发请求直接结束
3
发请求，流式接收
按会话日志推出给模型的历史，发出后冻结；失败重试沿用同一份拼装
4
执行工具
每个调用走一遍工具管道（下一节）
5
要不要再来一步
工具结果要交回模型，或者又来了新输入
是 → 回到第 1 步
否 → agent/turn-stopping，插件还能让它再跑一步
✓
turn/end
turn、step、消息、工具调用都作为事件写进会话日志
运行中的用户输入分两种：followup() 排到后面，steer() 插进当前这轮改方向。

会话日志是唯一事实来源

规则：模型看到的，必须都在日志里

只追加不修改的事件日志。每一次发给模型的请求，都能从日志完整重建。插件想给模型加新输入，必须先定义成会话事件。

↻

恢复

进程重启后从日志接着跑。

⑂

分叉

在某一轮的边界复制前缀，开一个新会话。

▤

界面

UI 渲染、导出记录都读日志。

◎

遥测和回放

日志转成 JSONL 就是可回放的 trace。

  • 失败也记：失败、重试、取消的模型输出记成 assistant/attempt，留痕但不进模型历史
  • 格式有版本：JSONL 文件按版本命名，旧版本打开时逐级迁移，原文件不改不删

工具管道

1
记录 tool/call
执行前先写进日志，UI 显示待执行卡片
2
tools/pre-execute
Hook、权限、沙箱都挂在这里，按顺序过
allow → 继续
ask → 弹一次审批，没人能答就拒绝
deny → 跳过工具，把拒绝原因交给模型
3
守卫（guard）
只能拒绝或弃权，不能放行，前面的插件绕不过它
4
tools/execute 包住真正执行
超时、重试、计时挂在这层；写文件还要过 fs/write-intent 检查
5
tools/post-execute
接受、拦截、替换结果，或附加上下文
✓
记录 tool/result
一次调用只有一个结果交给模型；附加的上下文排在这批结果之后
2、4、5 是「瀑布」事件：每个监听者处理完要调用 next() 交给下一个，所以多个插件可以层层包裹同一次调用。

1两种工具模式：Native 和 PTC

NativePTC（Programmatic Tool Calling）
模型看到什么每个工具的 schema只有一个 run_code 工具，加一份生成的 SDK
怎么调用一次发一批工具调用写一段代码，在代码里调用工具
好处简单直观能循环、并行、过滤结果，省掉多轮往返和 token
安全每个调用过管道代码里的每个子调用也照样过管道，有速率和并发上限
思路和 Claude Code 的 Code Mode 一样：让模型写代码批量调工具。

上下文与缓存

⇣

动态内容往后放

当前目录、文件变化这类会变的信息，作为一条用户角色的快照追加在历史后面，只在变化时才写新的，不改前缀。

▦

系统提示分段

每个插件贡献一段，有固定顺序。平时只追加更新；压缩之后才整体重建。

⇲

两条压缩路径

每步开始前检查上下文压力，自动压缩；请求因超长报错时走溢出恢复。手动压缩用同一个服务。

⌕

工具按步放行

每一步只放被允许的工具 schema。ToolSearch 式的渐进加载也是靠这个机制实现。

文档里专门写了插件对「KV Cache」的影响，说明设计时把缓存前缀稳定当成硬约束。DeepSeek API 从 2024 年起就有上下文缓存，命中部分按低价计费。
  • 项目说明：自动加载 AGENTS.md，也认 CLAUDE.md；子目录里的说明在读到那个目录时才注入
  • 长目标：/goal 让会话一直朝一个目标做，跨重启也保留；/loop 每轮结束自动接下一轮

权限与沙箱

两条独立的轴，拼成三个预设

沙箱模式管子进程能碰哪些文件，审批策略管工具调用要不要问人。

预设沙箱审批说明
read-only只读ask不让写文件
workspace-write只能写工作区ask默认，危险操作先问
danger-full-access不限制never不隔离也不问，只在一次性环境用
  • 沙箱后端：Linux 用 bubblewrap / Landlock，macOS 用 Seatbelt，Windows 用 ACL
  • 只管文件：官方文档说沙箱模式只约束文件效果，网络不在沙箱范围内
  • 执行程度会上报：后端会报告是完全执行还是部分执行（比如旧内核），调用方可以据此拒绝
  • Auto review：实验性插件，用模型代替人审批，它自己的文档也提醒可能放过不安全的操作
官方 SAFETY.md：项目没有做过安全审计，不能当成安全或可上生产的软件。建议在虚拟机、容器或单独的系统用户下运行。

默认会上传什么

用 DeepSeek 官方 API 时，请求里默认多带两个字段

插件字段内容默认
session-log-deepseekdsh_session_log增量上传会话日志：你的消息、系统提示、工具调用和结果。每次请求最多 8 MiB开
plugin-package-inventory-deepseekdsh_plugin_packages当前启用的插件包名和版本开
  • 只针对官方 API：换成第三方模型或自定义接口，不会加这两个字段
  • 怎么关：设置 → 通用里关掉上传开关；要对所有会话生效，在补丁里把这两行设成 enabled: false
  • 重新打开会补传：据第三方实测引用的插件文档，关闭期间的记录在重新打开后会一起上传
在公司或客户的代码库里用之前，先决定要不要关。默认值都写在源码和文档里，但快速上手教程没提。

常见问题

Q1harness 是什么？为什么模型厂商要自己做？
参考答案
  • 定义：模型之外的运行时，管工具调用、文件编辑、命令执行、上下文和会话状态
  • 影响大：同一个模型换 harness，任务完成率差别明显，工具设计和上下文管理都在这层
  • 厂商自己做：模型和运行时一起调，比如按自家 KV cache 的特点设计提示词结构；也能收集真实的 Agent 轨迹改进模型
Q2「一切皆插件」的好处和代价？
参考答案
  • 好处：没有特权内核，任何一层都能用补丁替换；插件注册是可撤销的副作用，能热重载
  • 好处：适合当底座，用配置拼出不同产品（Web、CLI、SDK、ACP）
  • 代价：概念多、插件数量多，排查问题要看拼出来的整棵树
  • 代价：顺序和依赖靠约定，所以要有「守卫」这种不能被绕过的机制兜底
Q3为什么要求「模型看到的都在日志里」？
参考答案
  • 可重建：任意一次请求都能从日志还原，方便排查模型为什么这么做
  • 单一来源：恢复、分叉、UI、遥测都从同一份日志推出，不会状态不一致
  • 可回放：日志就是 trace，能拿来复现问题和做评测
Q4PTC 模式比直接调工具好在哪？有什么风险？
参考答案
  • 省：只暴露一个 run_code，不用把所有 schema 放进上下文
  • 快：一段代码里循环、并行、过滤，少很多次模型往返
  • 风险：代码能组合出规则没预料到的调用；DSH 的做法是每个子调用照样过工具管道，并限制速率和并发
Q5沙箱和审批为什么要拆成两条轴？
参考答案
  • 管的东西不同：沙箱是操作系统层面能碰到什么，审批是要不要先问人
  • 组合更灵活：只读加审批、可写工作区加审批、全放开不审批，按场景选
  • 纵深防御：审批漏了，沙箱还能挡住越界写入；但网络不在沙箱里，要另外控制
