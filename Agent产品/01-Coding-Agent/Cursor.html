关键组件

⇥

Tab 模型

自研小模型，根据最近的编辑预测下一处改动，可以跨行、跳位置。

🩹

Apply 模型

把大模型写的草稿改动快速合并进完整文件，主模型不用重写整个文件。

🤖

Agent 模式

能搜代码、读写文件、跑终端命令、看报错再改，命令执行可设为需确认。

🗂

代码库索引

代码切块做向量嵌入，支持语义搜索，@codebase 一问全库。

📏

Rules

.cursor/rules 下的规则文件，可按路径匹配自动注入，也有用户级全局规则。

🧩

扩展点

MCP 接外部工具，@ 引用文件、文档、网页，Bugbot 做 PR 审查。

代码索引与上下文

先把代码库变成可检索的

  • 切块嵌入：按语法结构切代码块，算向量存到服务端
  • Merkle 树增量同步：只上传哈希变化的文件，不用每次全量重建
  • 隐私：服务端存向量和混淆路径，原始代码不落盘；遵守 .cursorignore
  • 混合检索：语义搜索 + grep 精确搜索，Agent 自己挑工具
  • 显式上下文：@文件 / @文件夹 / @Docs，用户直接指定

常见问题

Q1为什么要单独搞一个 Apply 模型？
参考答案
  • 延迟：让大模型重写整个文件太慢，草稿 diff 短得多
  • 成本：合并是机械活，小模型够用，单价低
  • 可靠：大模型写的 diff 行号常对不上，Apply 模型专门处理这种合并
Q2代码库索引怎么保持最新？
参考答案
  • Merkle 树：比对目录哈希，只找出变了的文件
  • 增量重嵌入：只对变动的块重新算向量
  • 兜底：索引可能滞后，Agent 还能 grep 和直接读文件
Q3向量检索和 grep 各适合什么场景？
参考答案
  • 向量：模糊的问题，比如「登录逻辑在哪」，不知道关键词时
  • grep：精确的符号名、报错字符串，结果准、永远最新
  • 结论：两者都给 Agent，让模型按问题选
Q4Rules 和直接写进 prompt 有什么区别？
参考答案
  • 持久：存在仓库里，团队共享，跟着代码版本走
  • 按需：可按文件路径匹配才注入，不浪费上下文
  • 分层：项目规则和用户规则叠加
