逐个讲清

1Tool / Function calling

最底层的机制。程序声明「有哪些函数、参数长什么样」，模型输出调用意图，程序执行后把结果作为 tool_result 回填。

其他所有「能力类」扩展，最后都要落到这一层。

Tools 可调用的函数，Resources 可读的数据，Prompts 提示词模板。

4CLI：让 Agent 直接用命令行

# 不接任何 MCP，模型直接在 Bash 里组合命令

🧠

模型本来就会

训练数据里有大量 man page、脚本和问答，gh / git / kubectl 不用教。

🔗

能组合

管道、grep、jq 一行过滤完，只把需要的几行交给模型。

🪶

省 token

不用常驻几十个工具 schema，只有一个 Bash。

5Plugin

my-plugin/
├── .claude-plugin/plugin.json   # 清单：名字、版本、描述
├── skills/review/SKILL.md
├── agents/reviewer.md           # Subagent 定义
├── hooks/hooks.json
└── .mcp.json                    # 要连的 MCP server
  • 本身不是新能力：只是容器，装的是 Skills、Subagent、Hook、MCP
  • 分发：从 marketplace（一个带清单的仓库）按名字安装，有版本、能更新
  • 命名空间：插件里的 Skill 叫 /my-plugin:review，多个插件不冲突
  • 注意：启用后每个会话都在，描述常驻上下文，Hook 每次都触发

7Hook

// settings.json：每次改文件前先跑脚本，exit 2 就拦下
{ "hooks": { "PreToolUse": [{
    "matcher": "Edit|Write",
    "hooks": [{ "type": "command", "command": "./block-env.sh" }]
}] } }
  • 事件：SessionStart、UserPromptSubmit、PreToolUse、PostToolUse、Stop 等
  • 能做：拦截、改参数、给模型补充上下文、发通知、记审计日志

8A2A（Agent2Agent）

🪪

Agent Card

一份 JSON 名片：我是谁、会什么、地址、怎么鉴权。用来发现对方。

📦

Task

委派的任务有状态：进行中、需要补充信息、完成、失败。适合长任务。

📨

Message / Artifact

过程中来回发消息，最后交付产出物（文件、结构化数据）。

  • 不透明：调用方看不到对方内部用了什么模型、工具、提示词
  • 来源：Google 2025 年发布，后捐给 Linux 基金会，2026 年发布 1.0

容易混的几组

1MCP vs Tool

MCP 是「工具怎么接进来」的协议，Tool 是「模型怎么调用」的机制

MCP server 暴露的工具，被客户端翻译成普通 tool 定义交给模型。在模型眼里，MCP 工具和自己写的工具没有区别。

自己写 ToolMCP
代码在哪Agent 程序里独立的 server 进程或远程服务
复用换个 Agent 要重写写一次，所有支持 MCP 的客户端都能用
谁维护你自己通常是服务提供方（GitHub、Notion 官方）
适合只给自家 Agent 用的内部函数要给很多 Agent / 很多人用的服务
类比 USB：Tool 是「设备能干什么」，MCP 是「统一的接口」。

2MCP vs CLI：近一年争论最多的一组

2026 年初开始，不少工程师认为「有现成 CLI 就别接 MCP」，于是有了一轮 MCP vs CLI 的讨论。结论不是谁取代谁，而是各有适用场景。

⌨

CLI 胜在

模型本来就会用；管道组合灵活；不用常驻 schema，token 省；没有额外的 server 进程要维护。

🔌

MCP 胜在

OAuth 鉴权和细粒度权限；跨客户端标准化；远程 SaaS 没有 CLI 也能接；参数和返回是结构化的，好校验。

场景更合适原因
本地开发查 PR、看日志CLIgh、git 现成，已登录
排查 k8s 集群CLIkubectl + grep 一行过滤
网页版 / 手机版 Agent 读 NotionMCP没有终端，只能走远程服务 + OAuth
企业给全员开放内部系统MCP统一鉴权、按人授权、可审计
浏览器自动化、设计稿读取MCP交互有状态，没有好用的 CLI
CLI 的风险：给了 Bash 等于给了任意执行，要靠权限规则和沙箱兜住。MCP 的问题：不做延迟加载时，工具 schema 很占上下文。

3Skills vs MCP

SkillsMCP
给模型的是知识和流程：「怎么做」能力：「能做什么」
形态Markdown + 脚本，放在本地文件夹一个运行中的服务
加载渐进式：描述 → 正文 → 附件工具定义（全量或延迟加载）
例子「我们的 SQL 规范、表结构、常用查询」「连上数据库执行 SQL」
最好的用法是配合：MCP 负责连上数据库，Skill 告诉模型表结构和查询习惯。Skill 也可以直接写「用 gh 做这些事」，把 CLI 变成一套流程。

4Skills vs Subagent

📘

Skill = 说明书

内容加进当前上下文，由当前 Agent 照着做。适合参考资料、固定流程。

👷

Subagent = 外包工人

新开一个独立上下文去干活，只交回结论。适合要读很多文件、可以并行的任务。

  • 看问题出在哪：缺知识用 Skill；上下文要爆了用 Subagent
  • 能组合：Subagent 定义里可以预装 Skill；Skill 也能设成 context: fork 在子 Agent 里跑

5Hook vs 写在提示词里的规则

提示词 / CLAUDE.md 里写Hook
执行方式模型读了之后自己遵守运行时到点就跑
可靠性大概率遵守，长对话里可能忘每次都执行，确定
适合需要判断的偏好：代码风格、命名必须遵守的规则：禁改 .env、改完跑 lint
一句话：提示词是请求，Hook 是强制。规则绝对不能破，就写成 Hook。

6MCP vs A2A

🔧

MCP：Agent ↔ 工具

对方是被调用的能力，输入输出明确，一般很快返回。

🤝

A2A：Agent ↔ Agent

对方是有自主性的 Agent，可能跑很久、中途反问、最后交付产出物。

MCPA2A
对方内部一个函数不透明，自己有模型和工具
交互一次调用，一次结果有状态的任务，可多轮、可推送进度
发现客户端配置 server 地址读对方的 Agent Card
例子旅行 Agent 调航班查询 API旅行 Agent 委托酒店方的预订 Agent
两者是互补关系：一个 Agent 用 MCP 接自己的工具，用 A2A 和别的 Agent 协作。Subagent 是同一个产品内部的分工，A2A 是跨团队、跨厂商的。

1

常见问题

Q1有了 Function calling，为什么还需要 MCP？
参考答案
  • 层次不同：Function calling 是模型调用工具的机制，MCP 是工具接入的协议
  • 解决 M×N：没有 MCP，每个 Agent 都要给每个服务写一遍集成；有了 MCP，服务方写一次 server
  • 附带能力：OAuth 鉴权、远程传输、Resources / Prompts 等标准化
  • 模型无感：最终仍转换成普通 tool 交给模型
Q2有人说「CLI 比 MCP 好」，你怎么看？
参考答案
  • CLI 的优势成立：模型熟悉、能用管道组合、token 省、少维护一个服务
  • 但有前提：要有终端、有成熟 CLI、本机已登录，通常是单人本地开发
  • MCP 不可替代的：网页 / 移动端 Agent、OAuth 按人授权、企业统一审计、没有 CLI 的 SaaS
  • MCP 的 token 问题：可以用延迟加载工具 schema 缓解，Claude Code 默认就这么做
Q3Skills 和把说明写进系统提示有什么区别？
参考答案
  • 加载时机：系统提示每次全量；Skill 平时只占一句描述，用到才加载正文
  • 能带文件：Skill 是文件夹，可以带脚本和参考文档，脚本代码不进上下文
  • 可复用：遵循 Agent Skills 开放标准，同一个 Skill 能在多个 Agent 产品里用
  • 选法：每次都要知道的短规则放系统提示 / CLAUDE.md，长的、偶尔用的做成 Skill
Q4「禁止修改 .env」应该写在哪？
参考答案
  • 写成 PreToolUse Hook：匹配 Edit / Write，路径是 .env 就 exit 2 拦截，原因回给模型
  • 或者用权限 deny 规则：同样是确定性的
  • 不要只写在提示词里：那只是请求，长对话里模型可能忘
  • 可以两者都写：提示词让模型别去试，Hook 兜底
Q5MCP 和 A2A 是竞争关系吗？
参考答案
  • 不是：MCP 连 Agent 和工具，A2A 连 Agent 和 Agent
  • 区别：工具是透明的函数、一次调用；Agent 是不透明的、有状态的长任务
  • 组合：一个 Agent 内部用 MCP 接工具，对外用 A2A 和其他 Agent 协作
  • 现状：两个协议都已在 Linux 基金会下托管
