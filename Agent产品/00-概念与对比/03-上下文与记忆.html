Context engineering 是什么

模型每一轮只看得到窗口里的 token：决定每一轮往窗口里放什么、不放什么，就是 context engineering
目标
用最少的高信号 token 换最好的结果
原因
窗口有限，内容越多注意力越分散
来源
Anthropic、Manus、Cognition 2025 年的工程文章
Prompt engineeringContext engineering
管什么怎么写提示词，尤其是系统提示窗口里的全部内容：提示、工具、记忆、检索结果、历史
什么时候做写一次，上线前调好每一轮都要重新挑选
典型场景单次分类、改写、生成跑几十上百轮的 Agent
关系后者包含前者。Anthropic 把它看作 prompt engineering 的自然延伸
一句话：Agent 每调一次工具，窗口就多一截。context engineering 管的是这一截要不要留、留多少、放在哪。

上下文里放什么

📜

系统提示

角色、规则、输出格式。写到「刚好够用」，别塞一堆 if-else。

🧰

工具定义

每个工具的名字、说明、JSON Schema。工具多了光定义就上万 token。

🧠

记忆

跨会话留下的偏好和经验，比如 CLAUDE.md、MEMORY.md。

🔎

检索结果

RAG 召回的片段，或模型自己 grep / 搜索拿回的内容。

💬

对话历史

用户消息、模型回复、每次工具调用和结果。增长最快的一块。

📌

少量示例

挑几个典型例子，不要罗列所有边界情况。

Agent 的输入远大于输出。Manus 报告平均输入:输出约 100:1，所以成本和延迟主要花在「读上下文」上。

上下文腐化

窗口装得下，不等于模型用得好

token 越多，模型从中准确找回信息的能力越差。这叫 context rot。所有模型都有，只是下降快慢不同。

n²

注意力被摊薄

每个 token 都要和其他 token 建立关系，长度翻倍，关系数翻四倍。

📉

训练里长序列少

模型见过的长文本比短文本少，处理远距离依赖的经验也少。

🌀

中间容易丢

放在长上下文中段的信息更容易被忽略（lost in the middle）。

  • 表现：忘了最初的目标、重复已经做过的步骤、被早期的错误信息带偏
  • 结论：把上下文当成有限预算，不是越多越好。更大的窗口也解决不了

上下文变长怎么办

1压缩（compaction）

快满时，让模型把历史总结成一份摘要，用摘要开一个新窗口继续干。

Claude Code 的做法：保留架构决策、没解决的 bug、实现细节，丢掉冗余的工具输出，再带上最近读过的 5 个文件。

  • 难点：删多了，后面才发现要用的细节已经没了
  • 调法：先保证不漏（召回），再慢慢删多余的（精度）

2工具结果裁剪

  • 清掉旧结果：十几轮前的 cat 输出，模型不用再看原文。这是最轻、最安全的压缩
  • 工具本身返回少：分页、截断、只返回摘要，别一次吐 5 万行日志
  • 可恢复：网页正文可以丢，URL 要留；文件内容可以丢，路径要留（Manus 的做法）

3把状态写到文件（外部化）

✅

todo.md

Manus 每做完一步就改一次待办，相当于把目标重新念到上下文末尾，模型不容易跑偏。

📝

NOTES.md

Agent 自己记笔记：进度、踩过的坑、下一步。压缩或重启后读回来接着干。

📂

文件系统

大小不限、天然持久，Agent 自己能读写。Manus 称之为「终极上下文」。

Prompt caching

模型每轮都重读整个上下文，缓存让「重读」变便宜

服务端把算过的前缀（KV cache）存起来。下一次请求的开头一模一样，这部分就直接复用，不再重算。

Manus 文中举例：Claude Sonnet 缓存命中的输入 0.30 美元 / 百万 token，未命中 3 美元，差 10 倍。

省时间

首 token 延迟（TTFT）明显下降。Manus 认为命中率是生产 Agent 最重要的单一指标。

RAG vs Agentic search

📚

RAG（向量检索）

提前把文档切块、算向量、建索引。提问时按语义相似度召回 Top-K 片段，一次性塞进上下文。

🔍

Agentic search

不预处理。模型手里只有路径、链接这类「指针」，自己用 grep、glob、搜索工具一步步找，用到才读。

RAGAgentic search
速度快，一次检索慢，要多轮工具调用
新鲜度索引会过期，要重建永远是当前状态
精确匹配函数名、报错串容易召回不准grep 一找一个准
模糊语义「讲退款政策的段落」很擅长要靠模型猜关键词
规模百万级文档也行数据太大时搜索成本高
工程量切块、向量库、同步、权限只需要好用的搜索工具
场景更适合
代码库Agentic search。Claude Code 不建索引，直接 grep
海量客服知识库RAG，问题大多是语义匹配
法律、财务文档混合：先检索一批，再让模型自己深挖
开放式调研多步搜索，边看边改查询词
Claude Code 就是混合式：CLAUDE.md 开局直接放进上下文，其余文件靠 glob / grep 按需读。

记忆分类

模型本身不记事，「记忆」都是工程做出来的

按存多久分短期 / 长期，按存什么分语义 / 情景 / 程序性。

短期记忆长期记忆
范围一次会话内跨会话
放在哪上下文窗口里的对话历史窗口之外：文件、数据库
怎么进上下文天然就在启动时加载，或按需检索
主要问题窗口满了要压缩写什么、怎么找、何时删

语义记忆

事实。「用户用 Python」「项目用 pnpm」。

🎞

情景记忆

发生过的事。「上周三那次部署因为缺环境变量失败了」。常用来当示例。

⚙

程序性记忆

怎么做。系统提示、规则、Skills，比如「提交前先跑 lint」。

这套分法借自认知科学，Agent 领域常引用 CoALA 论文和 LangChain 的记忆文档。

长期记忆怎么实现

方式怎么做优点缺点
文件 + 索引每条记忆一个文件，索引文件常驻上下文，相关的再读全文（Claude Code auto memory）简单，人能看能改，可进 git条数多了索引太长
向量库记忆转成向量，按相似度召回（Mem0 等）能存很多，语义召回召回不准、难更新、难解释
知识图谱抽成「实体-关系-实体」，带时间（Zep / Graphiti 等）能回答关系和时间类问题抽取成本高，系统复杂
厂商 memoryChatGPT、Claude 应用自带的记忆；Claude API 的 memory tool 让模型读写一个记忆目录开箱即用不透明，难迁移

常见问题

Q1窗口已经 100 万 token 了，还需要 context engineering 吗？
参考答案
  • 腐化：装得下不等于用得好，越长召回越差
  • 成本：每轮都重读全部上下文，缓存也要按 token 计费
  • 延迟：上下文越长，首 token 越慢
  • 结论：大窗口是余量，不是可以乱塞的理由
Q2压缩和缓存有冲突吗？
参考答案
  • 有：压缩改写了历史，前缀变了，下一轮缓存不命中
  • 缓解：在任务间隙手动压缩，别在任务中途频繁压
  • 优先轻手段：先清旧工具结果，再考虑整体摘要
Q3工具太多，为什么 Manus 不按需加载工具？
参考答案
  • 缓存：工具定义在上下文前部，增删一个，后面全部重算
  • 混乱：历史里调用过的工具突然没了，模型会乱调或违反 schema
  • 替代：定义全保留，解码时遮罩不该用的工具名
  • 另一条路：Claude Code 的 ToolSearch 只放工具名，定义集合不变，也能保住缓存
Q4RAG 和 Agentic search 怎么选？
参考答案
  • 看数据：经常变、要精确匹配（代码）选 agentic search
  • 看规模：海量、相对静态、语义查询（知识库）选 RAG
  • 看延迟：要一次出结果选 RAG，能接受多轮选 agentic
  • 常见答案：混合，先召回一批，再让模型自己深挖
Q5设计一个 Agent 的长期记忆，要考虑哪些点？
参考答案
  • 存什么：偏好、纠正、外部查不到的约束；能查到的不存
  • 存哪：条数少用文件 + 索引；条数多再上向量库或图谱
  • 怎么读：核心记忆常驻，其余按需检索
  • 怎么忘：去重、覆盖旧条目、记错能删、过时会过期
  • 安全：防止不可信内容被写进记忆
