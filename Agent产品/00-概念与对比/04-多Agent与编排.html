单 Agent 还是多 Agent

多 Agent 用更多 token 和协调成本，换并行和干净的上下文
单 Agent
一个循环、一份历史
多 Agent
多个循环，各有自己的窗口
token 开销
Anthropic 数据：约为聊天的 15 倍
单 Agent多 Agent
上下文连续，每一步都看到之前所有决定各自隔离，子任务不污染主窗口
并行串行，长任务慢多个方向同时跑
token少Agent 约为聊天的 4 倍，多 Agent 约 15 倍

两种观点

A

Anthropic：多 Agent 做调研更强

《How we built our multi-agent research system》，2025-06。

  • Opus 4 做 lead + Sonnet 4 做子代理，内部调研评测比单个 Opus 4 高 90.2%
  • BrowseComp 上，token 用量单独解释 80% 的表现差异
  • 本质：多个窗口 = 能花更多 token 去并行思考
  • 适合广度优先、方向互相独立的问题
C

Cognition：别做多 Agent

《Don't Build Multi-Agents》，2025-06，Devin 团队。

  • 原则 1：共享上下文，而且共享完整轨迹，不只是单条消息
  • 原则 2：每个动作都带着隐含决定，决定冲突结果就坏
  • 默认用单线程 Agent，太长就加一个专门压缩历史的模型

1Cognition 的例子：做一个 Flappy Bird

1

合并时对不上
把原始任务也传给子代理，风格仍可能不一致
两边其实不矛盾：调研类任务子方向独立、只读、结果能合并，适合多 Agent；写代码这类步骤之间强依赖的任务，单 Agent 更稳。Anthropic 原文也说多数编程任务可并行的部分不多。

5脚本化编排（workflow）

  • 把计划写成代码：循环、分支、中间结果都在脚本里，主 Agent 只收最终答案
  • 规模：一次几十到几百个 Agent，比如全仓库扫 bug、500 个文件的迁移
  • 能固化质量流程：每条发现都派独立 Agent 反向核对，过了才报告
  • 可复跑：脚本存下来就是一个命令

子代理的上下文传递和结果回收

1派任务时给什么

子代理只知道你写进任务描述的东西。Anthropic 要求每个任务描述都包含：

🎯

目标

要回答什么问题。

📋

输出格式

列表、表格，还是带出处的结论。

🧰

工具和来源

去哪找、用什么工具。

🚧

边界

哪些不归它管，避免重复和遗漏。

传法做法取舍
只传任务描述全新窗口，写一段说明最省 token，但容易误解
传完整历史（fork）复制父对话不用重新交代背景，还能命中父的缓存；窗口一开始就不干净
传引用给文件路径、URL，让它自己读精确，传递成本低

2结果怎么收回来

  • 摘要：子代理可能用了几万 token，只交回 1,000~2,000 token 的结论
  • 写文件：大结果存到文件系统，只把路径交回，避免「传话游戏」一层层丢信息
  • 结构化：要求固定格式，方便主 Agent 合并、去重
  • 要验证：子代理的话和工具结果一样，当数据看，必要时再派一个去核对

A2A 协议

MCP 让 Agent 接工具，A2A 让 Agent 接 Agent

Google 2025-04 发布，同年交给 Linux 基金会。让不同框架、不同公司做的 Agent 能互相发现、委托任务，不用暴露各自内部的提示、记忆和工具。

🪪

Agent Card

一份 JSON 名片，放在 /.well-known/ 下：我叫什么、能干什么、怎么认证。

📦

Task

一次委托，有状态：提交、进行中、需要输入、完成、失败。可以很长时间。

✉

Message / Artifact

过程中来回的消息，以及最终产出的文件或数据。

MCPA2A
连接对象工具、数据源另一个 Agent
对方听话执行，没有自己的判断自己会规划，可能反问
交互一次调用一次结果长任务，可流式、可推送进度

多 Agent 的 token 是数倍到十几倍
高价值任务 → 拆
高频低价值 → 不拆
4
谁持有计划？
选拓扑
模型逐轮决定 → orchestrator-worker
流程固定 → 图编排 / workflow 脚本
按领域分诊 → handoff
✓
按什么维度拆
按信息来源、按子问题、按模块；子代理以只读调研为主，写操作尽量留给一个 Agent
✓

适合拆

多方向调研、多个假设并行验证、大批量相同处理（每个文件一份）、独立审查。

✗

不适合拆

步骤强依赖的编码、要频繁来回沟通的任务、很小的改动、在意延迟的场景。

常见问题

Q1Anthropic 说多 Agent 好，Cognition 说别做，谁对？
参考答案
  • 任务不同：Anthropic 做的是调研，子方向独立、只读；Cognition 做的是写代码，步骤强依赖
  • 共同点：都把上下文当核心问题，都承认多 Agent 贵且难协调
  • 结论：能并行、能合并的用多 Agent；决定之间互相牵制的用单 Agent
Q2多 Agent 为什么能提升效果？
参考答案
  • 花更多 token：BrowseComp 上 token 用量解释了 80% 的差异
  • 干净窗口：每个子代理只看自己的任务，不被别的信息干扰
  • 并行：lead 同时起 3~5 个子代理，Anthropic 称复杂查询的调研时间最多缩短 90%
Q3Handoff 和 agent as tool 有什么区别？
参考答案
  • Handoff：控制权转移，新 Agent 接着和用户对话，默认带上之前的历史
  • Agent as tool：控制权不变，调用方拿到结果继续
  • 选法：按领域分诊（退款、技术支持）用 handoff；要一个主 Agent 统筹用 as tool
Q4子代理结果出错或互相矛盾怎么办？
参考答案
  • 事前：任务描述写清目标、格式、边界，减少误解
  • 事中：并行的子代理尽量只读，写操作集中到一个 Agent
  • 事后：派独立 Agent 核对，或让多个子代理交叉验证，冲突时回原始来源
Q5A2A 和 MCP 是竞争关系吗？
参考答案
  • 不是：MCP 接工具和数据，A2A 接其他 Agent
  • 区别：A2A 的对方有自己的判断，任务可以很长、要中途补信息
  • 常见组合：内部用 MCP 调工具，跨团队、跨公司用 A2A 委托
