Agent 基础

什么是 Agent

Agent = 大模型 + 工具 + 循环：模型自己决定下一步调哪个工具，看到结果再决定下一步，直到做完
大脑
LLM，负责决策
手脚
工具：搜索、读写文件、调 API
记忆
消息历史 + 外部文件
驱动
一个 while 循环
💬

聊天机器人

一问一答。模型只输出文字，不动手。

🔧

带工具的 LLM

能调一次工具，比如查天气再回答。下一步由程序写死。

🤖

Agent

调几次、调哪个、什么时候停，都由模型自己定。

判断标准只有一条：控制流在谁手里。写在代码里是 Workflow，交给模型是 Agent。

Workflow 和 Agent

Anthropic《Building effective agents》的划分

Workflow：LLM 和工具按预先写好的代码路径编排。

Agent：LLM 动态决定自己的流程和工具使用。

两者都叫 agentic system，地基是同一个：带检索、工具、记忆的增强版 LLM。

WorkflowAgent
谁定下一步代码模型
步骤数固定，提前知道不固定，做完才知道
可预测性高，好测试低，结果有波动
成本 / 延迟可控更高，轮数说不准
适合任务能拆成固定步骤开放问题，路径没法预先写

1五种 Workflow 模式

模式怎么做例子
Prompt chaining
提示链		上一步输出喂给下一步，中间可加检查点（gate）先写大纲 → 检查大纲 → 再写正文
Routing
路由		先分类，再交给对应的专用提示或模型客服：退款 / 技术问题 / 闲聊分开处理；简单问题走小模型
Parallelization
并行		分段（sectioning）各做一块；投票（voting）同一题做多次一个模型答题、另一个审核安全；多次审代码取多数
Orchestrator-workers
编排者-工人		中心模型运行时拆子任务，分给工人，再汇总改代码：要动哪些文件，看了需求才知道
Evaluator-optimizer
评估-优化		一个生成，一个打分给意见，循环到达标翻译反复润色；搜索多轮补漏
Orchestrator-workers 和并行的区别：并行的子任务是写死的，编排者的子任务是模型临时拆的。它已经很接近 Agent 了。

2文章的核心建议

  • 先用最简单的：一次 LLM 调用 + 检索 + 好的示例，往往就够
  • 按需加复杂度：单次不够再上 Workflow，Workflow 不够再上 Agent
  • 框架少用：先直接调 API，很多模式几行代码就能写；用框架也要看懂它底层在做什么
  • 工具要好好写：工具的说明和参数设计（ACI）值得和提示词花一样多的功夫

Function calling 原理

模型自己从不执行任何东西

它只输出一段结构化的调用意图：要调哪个函数、传什么参数。真正执行的是你的程序，执行完再把结果塞回对话。

1
程序声明工具
请求里带上 tools：名字、用途说明、参数的 JSON Schema
2
模型决定要不要调
看用户问题和工具说明，自己判断
不需要 → 直接回答文字
需要 → 输出 tool_use 块
3
程序解析并执行
校验参数、检查权限，然后真的去调 API / 查库 / 跑命令
4
回填 tool_result
用 id 对上是哪次调用；报错也照样回填，让模型自己改
↻
带着结果再请求一次模型
模型继续调工具，或者给出最终回答
// 1. 请求里声明工具
tools: [{ name: "get_weather", description: "查城市天气",
          input_schema: { city: "string" } }]

// 2. 模型返回：只是意图，没有执行
{ type: "tool_use", id: "toolu_01", name: "get_weather", input: { city: "上海" } }
stop_reason: "tool_use"

// 3. 程序执行后，以 user 消息回填
{ type: "tool_result", tool_use_id: "toolu_01", content: "小雨 18℃" }

// 4. 模型再看一遍完整对话，回答：上海今天小雨，18℃，记得带伞
📝

工具说明 = 提示词

模型只能看名字和 description 选工具。写不清就会选错、传错参数。

⚡

可以并行

一轮里能发多个互不依赖的 tool_use，程序并发执行，一起回填。

🔒

安全在程序这边

模型输出的参数是不可信输入，执行前要校验、限权限。

ReAct / Plan-and-Execute / Reflection

模式一句话优点缺点
ReAct想一步、做一步、看结果灵活，随时根据结果调整容易走一步看一步，绕远路
Plan-and-Execute先列完整计划，再逐步执行方向稳，计划可以给人审计划赶不上变化，要重新规划
Reflection做完先自查，再改质量更高，少犯低级错多花几轮 token 和时间

有外部信号最好

跑测试、编译、lint 的报错比「自己觉得哪里不对」靠谱得多。

👀

换个审稿人

同一个模型审自己容易放过错误，用独立的审核 Agent 或不同提示更有效。

📓

Reflexion

把失败后的反思写成文字存下来，下次尝试时带上，算一种经验记忆。

三者能组合：先 Plan，每步用 ReAct 执行，关键产出再 Reflection。Anthropic 的 evaluator-optimizer 就是 Reflection 的 Workflow 版本。

Agent loop 的停止条件

循环必须有出口，而且不能只靠模型说「我做完了」

模型可能提前收工，也可能原地打转。生产环境要正常出口 + 兜底出口都有。

类型条件例子
正常完成模型这轮没有调工具，只回文字stop_reason == "end_turn"
外部判定另一个模型或脚本检查目标是否达成测试全绿才算完；Claude Code 的 Stop Hook、/goal
预算上限最大轮数、token、费用、时间max_turns=50，超时 10 分钟
需要人要确认危险操作，或缺信息问用户删库前暂停；调用「提问」工具
异常不可恢复的错误，或检测到死循环同一个工具同样参数连续调 3 次
用户中断用户按 Esc / 取消保留已做的部分，下次可续
for turn in range(MAX_TURNS):              # 兜底：最多 N 轮
    resp = llm(messages, tools)
    if resp.stop_reason != "tool_use":     # 正常出口
        if verify(resp): break             # 外部再验一次
        messages += [resp, "还没达标：..."]; continue
    if over_budget() or looping(): break   # 费用 / 死循环
    messages += [resp, run_tools(resp)]

什么时候不该用 Agent

📋

步骤是固定的

发票识别 → 入库 → 发通知。写成 Workflow 更快、更便宜、好测试。

⚡

一次调用就够

翻译、摘要、分类。加检索和示例就能解决，不需要循环。

⏱

延迟和成本敏感

搜索框联想、实时对话。Agent 动辄几十秒、几十轮。

💥

错了无法回滚

转账、发全员邮件、改生产库。要么不给权限，要么每步人审。

❓

结果没法验证

没有测试、没有标准答案，Agent 做错了你也不知道。

📜

要求完全确定

合规审计要求每次走同样的路径、结果可复现。

反过来，适合 Agent 的特征：路径没法提前写、能自动验证结果、出错代价可控。写代码正好三条都占，所以 Coding Agent 最先成熟。

常见问题

Q1Agent 和 Workflow 的本质区别是什么？
参考答案
  • 控制流：Workflow 的步骤写在代码里，Agent 的下一步由模型运行时决定
  • 取舍：Workflow 可预测、便宜；Agent 灵活，但成本和结果有波动
  • 中间地带：orchestrator-workers 由模型临时拆任务，已经接近 Agent
  • 原则：从最简单的方案开始，确实需要灵活性再升级
Q2Function calling 时模型真的执行了函数吗？
参考答案
  • 没有：模型只输出 tool_use，包含函数名和参数 JSON
  • 程序执行：解析、校验、执行，再把结果作为 tool_result 回填
  • 靠 id 对应：一轮多个调用时，用 tool_use_id 区分
  • 好处：权限、沙箱、审计都在程序侧做，模型碰不到真实系统
Q3ReAct 和 Plan-and-Execute 怎么选？
参考答案
  • ReAct：环境多变、每步结果决定下一步，比如排查线上问题
  • Plan-and-Execute：任务长、结构清楚、希望人先审计划，比如大范围重构
  • 常见做法：两者结合，先出计划，每步内部用 ReAct，出意外再重新规划
Q4怎么防止 Agent 死循环或提前收工？
参考答案
  • 兜底上限：最大轮数、token、费用、时间
  • 重复检测：同样的工具和参数反复出现就打断
  • 外部验证：模型说完成后再跑测试或让独立模型判断，不达标就把原因塞回去继续
  • 人在环中：危险操作和信息不足时暂停问人
