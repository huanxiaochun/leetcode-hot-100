1花生 MG 项目深挖

Q1花生是一个什么产品？
一句话定位、给谁用、完整流程
参考答案
  • 一句话：给 B 站 UP 主用的 AI 视频 Agent，输入口播文稿（或上传录音），自动做出带配音、素材、MG 动画、BGM 的完整视频
  • 用户输入怎么处理：先判断输入类型，原则是能不改就不改
    • 完整口播稿：一字不改
    • 太短：问要不要扩写，保留原句
    • 大纲 / 要点：整理成口播稿，不编造
    • 夹着制作指令：删指令，正文不动
    • 只有题目：联网查资料后写新稿
  • 规划书里有什么：
    • 头部：标题、品类、画幅、音色、BGM、风格
    • 正文：场景 → 分镜（口播句）→ 动画（版式 + 要点）
  • 制作链路：建分镜 → 批量 TTS → 检索视频素材 → 生成 MG → 配 BGM → 每个分镜 GPU 渲染合成
  • 成片后：用自然语言继续改，比如「第 3 镜换个动画」「整片换音色」，Agent 只改受影响的分镜
Q2什么是 MG 动画？
和 AI 生视频的区别是关键
参考答案
  • MG = Motion Graphics：用文字、图形、图标、数据图表加动效讲内容，常见于知识科普、产品讲解、数据可视化
  • 和 AI 生视频的区别：AI 生视频输出像素，没法精确改一个字；MG 由结构化元素组成，文字准确、可以逐元素修改，适合信息类内容
  • 生成方式：MG 产物是 HTML 动画
    • LLM 先提取每段文稿的语义（要点、数据、对比关系）
    • 从模板库召回候选（模板按 26 个文稿分类组织），精排后填充内容组装
    • 按配音时长对齐动效节奏，套用全局风格（内置 14 套）
  • 为什么用模板 + LLM，不让模型从零写动画：模板保住设计下限和稳定性，LLM 负责理解和选择，兼顾质量和速度
Q3你在项目里做了哪些工作？遇到过哪些问题？
我的回答问题：不按预期加载 skill（插 reminder）；调错工具、工具参数有问题（校验，错误信息加到 loop 里重试）
做了哪些工作
  • MG 动画的实现：
    • 生成流程：LLM 提取每段口播的语义（要点、数据、对比关系）→ 从模板库召回 → 精排 → 填充组装成 HTML 动画
    • 风格统一：模板按 26 个文稿分类组织，整片套用一套全局风格（内置 14 套）
    • 音画对齐：按配音时长对齐动效节奏，流式返回每一段的结果
  • MG 工具接入 Agent：
    • 两个工具：produce_mg 从头生成（新加、换版式、改范围），revise_mg 局部改（改字、改颜色、换图）。局部改更便宜，也不会动到用户满意的部分
    • 版本记录：每次生成都留版本，想换回旧版免费
    • 花钱先问：一轮超过 3 个动画或用户没点名的重做，先问用户
遇到过哪些问题
  • 不按预期加载 skill：
    • 现象：成片后用户要改视频，模型不先读修改规划的 skill，直接动手改
    • 解决：每轮开始前按状态插 system-reminder，提示「已成片，要改先读 skill」
    • 踩坑：一开始每轮都插，会话只追加，同一条提醒被复制很多份，曾把输入顶到上限。改成读过 skill 或提醒过一次就不再插
  • 调错工具、参数不对：
    • 现象：该局部改的调了重做；范围跨场景；配音没好就做动画
    • 解决：执行前校验，不通过就返回原因，不执行、不扣费；错误信息回到 loop，模型自己改参数重试
    • 错误要写清怎么改：比如「写『分镜15』或『分镜5-分镜7』」，不只说「参数错误」
    • 限制重试：同参数不许重试，最多 2～3 次，还不行就告诉用户
  • 改了配音，动画对不上：
    • 现象：用户改口播或换音色后，配音时长变了，动画的节奏还是旧的
    • 解决：记录每个动画生成时的配音，变了就标记「配音已变」，告诉用户哪些动画需要重做，由用户决定
  • 模型过度调用：
    • 现象：整片做完后，模型又把 360 个分镜全部重做了一遍，又慢又费钱
    • 解决：工具描述写清「整片制作已包含所有步骤，不要逐镜重做」，再加评测用例防止回退
讲问题时按「现象 → 原因 → 解决」说，挑一个讲细，另外几个一句带过
Q4相比直接让 Opus 这类通用大模型做视频，花生的优势在哪？
面试官本质在问：壁垒是什么
参考答案
  • 完整链路：Opus 能写一段动画代码，但配音、素材检索、BGM、音画对齐、GPU 渲染、导出都没有；花生一句文稿出成片
  • 质量下限稳：模板库、14 套风格、设计规范兜底，不靠模型每次即兴发挥
  • 可编辑：产物是结构化工程，可以改单个分镜、单个动画，不用整片重来
  • 成本和速度：确定性步骤交给工程，子任务交给便宜模型，只在需要理解的地方调大模型
  • 领域积累：素材库、模板、B 站内容品类、用户的历史偏好，通用模型没有
Q5花生的用户画像是什么样的？
参考答案
  • 核心用户：B 站知识区、科普、财经、科技类 UP 主，以口播加信息图为主
  • 痛点：有内容，但剪辑和做动画太耗时，不会 AE，请人做成本高
  • 两种入口：只有文稿的（花生配音），已经录好口播的（上传音频，转写后对齐）
  • 扩展人群：运营、市场、教育从业者，做讲解和宣传视频
有真实数据（人群分布、留存、复购）的话一定要带上
Q6花生目前有哪些局限？
参考答案
  • 内容形态窄：适合口播加信息图，剧情、Vlog 这类偏画面叙事的内容做不好；只支持中英文
  • 效果上限受模板约束：风格多样性有限，高要求用户觉得像模板
  • 耗时和成本：长视频链路长，MG 生成、渲染都要排队等待
  • 隔离不彻底：CLI 子进程还没用 bwrap 包住，沙箱实例能访问内网，出站网络还没收紧
  • 精细修改难：自然语言描述「往左挪一点」这类细节，Agent 理解不稳定
Q7针对这些局限，你会怎么改进？
重点讲两条：沙箱化、Pro 版本
参考答案
  • 沙箱化：
    • 现状：一个项目一个阿里云 FC 实例，空闲 10 分钟回收；run 结束把会话和项目文件打快照存 S3，下次恢复
    • 进程隔离：用 bwrap 把 Agent 进程包起来，只能看到本项目目录
    • 网络隔离：出站改白名单，只放行网关和素材服务，禁止访问其他内网地址
    • 冷启动：迁到兼容 E2B 的 Agent Sandbox，用模板预构建和预热池，缩短首次响应时间
    • 开放平台：隔离做好后，开发者可以用 Claude Code plugin 格式写自己的视频工作流，跑在同一套沙箱里
  • Pro 版本：
    • 更强的模型：Pro 用户的规划和动效设计走更强的模型，普通版继续用 flash 类模型控成本
    • 更高的效果上限：允许 LLM 在模板基础上直接改写 HTML 动画，不局限于填充模板；支持品牌色、字体、片头片尾等自定义风格
    • 更长、更高规格：长视频、高分辨率导出，AI 生视频额度更多
    • 精细编辑：在画布上点选元素再用自然语言改，减少表达歧义
    • 体验：渲染优先队列，多分镜并行生成
  • 效果衡量：扩充评测集，按成片率、阻断错误率、平均耗时、单片成本、用户修改轮数来跟踪

Q1你用过最好的 Agent 产品是什么？
我的回答Claude（Claude Code）

Q2作为用户，Claude 相比 Codex、DeepSeek 等，好在哪里？
我的回答想得更全面，不会像 Codex 那样写一堆测试文件、过度设计
参考答案
  • 模型层：理解意图准，改动范围克制，代码风格贴近已有项目
  • Harness 层：
    • 工具设计细：Edit 按原文精确替换，不整文件重写，改动小、出错容易发现
    • 上下文工程：CLAUDE.md 项目规则、自动压缩、子 Agent 隔离上下文、工具按需加载
    • 可扩展：Skills、Hooks、MCP、斜杠命令，团队能把经验沉淀成可复用流程
    • 可控：权限模式、Plan 模式先出方案再动手，危险操作先确认
Q3追问：写多余测试、过度设计，是模型的问题还是 Agent 的问题？
面试官观点是 GPT 模型的问题
参考答案
  • 主要是模型：这类倾向来自后训练。如果 RL 的奖励是「测试通过」，模型就学会了多写测试、多做防御
  • Harness 能放大，也能缓解：系统提示里写「不做没要求的功能」「完成就停」，能压住一部分；反过来，鼓励「每次都要写测试验证」的提示会放大它
  • 怎么证明：控制变量。同一个 Harness 换模型（如 OpenCode 分别接 Claude 和 GPT），或同一个模型换 Harness，看行为跟着谁变
  • 结论：同意主要是模型问题，但做 Agent 的人不能只怪模型，要用提示、工具和评测把行为约束住
这题的加分点是给出「怎么验证」，而不是只站队
Q4Claude 有哪些不好的设计？
我的回答很多临时诉求被记进了 memory
参考答案
  • 记忆写入不分轻重：一次性的要求被当成长期偏好，之后每次会话都会受影响；记忆也会过时，和代码现状不符
  • 压缩丢细节：长会话自动压缩后，前面的报错原文、约定的细节可能丢失
  • 权限确认疲劳：确认弹窗太多，用户干脆开全部放行，反而更不安全
  • 子 Agent 是黑盒：主 Agent 只拿到摘要，子 Agent 的错误会以同样自信的口吻带回来；并行开多个时 token 消耗突增
  • 系统提示膨胀：Skills、MCP 工具一多，描述列表占掉大量上下文（后来改为工具按需加载，缓解了这一点）
  • 过早报完成：没真正验证就说「已完成」，需要用户再检查
Q5临时诉求被记进 memory，怎么解决？
我的回答压缩时统一判断会话里的诉求是临时还是永久
我的回答对吗
  • 方向对：压缩时能看到整段会话，比听到一句话就判断准。比如先说「这次别写测试」，后面又说「以后都别写」，放在一起看才分得清
  • 可以主动说的加分点：当前会话里，用户的要求本来就在上下文中，不需要马上写进记忆。推迟到压缩时统一判断，本次会话的效果不受影响
  • 不足一：时机不全：短会话还没触发压缩就结束了，会漏判，所以会话结束时也要判断一次
  • 不足二：单次会话判断不了「永久」：一个要求是不是长期偏好，最可靠的信号是它在别的会话里再次出现。只看一次会话，本质上还是在猜
  • 不足三：不只有临时和永久两种：有的只对当前项目有效，有的对所有项目有效
  • 不足四：只管写入，不管存量：代码改了、偏好变了，旧记忆会过时
  • 不足五：判断靠模型，会出错：要有纠错入口和衡量指标
完整方案
  • 判断时机：压缩时和会话结束时，两处都统一判断
  • 分层存储：先写成带有效期的「候选记忆」；同类诉求跨会话再次出现，或用户明确说「以后都这样」，才升级为长期记忆
  • 标明作用范围：本次会话 / 本项目 / 全局三档，召回时按范围过滤
  • 召回时校验：记忆里提到的文件、函数先确认还存在；和当前指令冲突时以当前指令为准
  • 用户可见可改：写入长期记忆时告诉用户一声，提供查看和删除入口
  • 可衡量：统计记忆被召回后用户纠正的比例，作为误记率
面试这样答
我会在压缩和会话结束时统一判断。这时能看到完整上下文，而且当前会话的要求本来就在上下文里，推迟写入不影响效果。但单次会话很难判断一个要求是不是长期偏好，所以先存为带有效期的候选记忆，并标明作用范围；跨会话再次出现，或者用户明确说「以后都这样」，才升级为长期记忆。召回时先校验内容是否还成立，用户也能查看和删除。最后用误记率衡量效果。

Q1726. 原子的数量（困难）
给一个化学式，如 K4(ON(SO3)2)2，按字典序输出每种原子的个数：K4N2O14S4
思路
  • 题目：leetcode.cn/problems/number-of-atoms
  • 题解：18-字节高频/0726-原子的数量（动画 + C++ / Python）
  • 栈 + 哈希表：每层括号一张表。遇 ( 压一张新表；读到原子把数量加进栈顶；遇 ) 读倍数 k，弹出栈顶，每个数量 ×k 加回上一层
  • 易错：) 后没数字时倍数是 1；原子名是大写加若干小写；输出按字典序，数量 1 不写
  • 复杂度：最坏 O(n²)（层层嵌套，每次出栈都重乘），空间 O(n)
  • 同类题：394 字符串解码、224 基本计算器
